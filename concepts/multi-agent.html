Section 1

Why Multi-Agent?

Single agent limitations:

  • Context window overflow on large tasks
  • Single model can't specialize simultaneously in multiple domains
  • No parallelism
  • Single point of failure

Multi-agent enables:

  • Parallelism (10 agents in parallel = 10× throughput)
  • Specialization (researcher + coder + reviewer)
  • Cross-checking (agents critique each other)
  • Decomposition (break large tasks into bounded subtasks)
⚠
Multi-agent adds orchestration overhead, communication latency, and debugging complexity. Start with a single agent. Add multi-agent only when you've hit a ceiling.
Section 2

Patterns: Orchestrator–Subagent

The dominant pattern: one orchestrator LLM decomposes the task and delegates to specialized subagents

Orchestrator responsibilities: task decomposition, subagent selection, result synthesis, error handling

Subagent responsibilities: execute a bounded subtask, return structured result

Example: orchestrator dispatch pattern

# Orchestrator decides which subagent to call orchestrator_result = llm.invoke(f""" Task: {task} Available agents: researcher, coder, reviewer Return JSON: {{"agent": "...", "subtask": "..."}} """) dispatch = parse_json(orchestrator_result) subagent_result = agents[dispatch["agent"]].run(dispatch["subtask"]) # Orchestrator synthesizes final = llm.invoke(f"Synthesize: {subagent_result}")
✓
Pass structured outputs between agents (JSON, Pydantic models) rather than free text. Free text between agents accumulates noise — each hop adds interpretation variance.
Section 3

Patterns: Parallel and MapReduce

Parallel execution: independent subagents run simultaneously, results merged by orchestrator

MapReduce for LLMs: map = process each document chunk with an agent, reduce = synthesize all chunk results

Use cases: summarizing 100 documents simultaneously, running multiple analysis perspectives, cross-validation by independent agents

Example: parallel agent dispatch with asyncio

import asyncio async def run_agent(agent, subtask): return await agent.arun(subtask) async def parallel_analysis(document_chunks): tasks = [run_agent(analyst, chunk) for chunk in document_chunks] results = await asyncio.gather(*tasks) return synthesizer.run(f"Combine: {results}") # 10 chunks processed in parallel instead of serially summary = asyncio.run(parallel_analysis(chunks))
Pattern Latency Quality Use case
Sequential N × single latency Each step uses prior context Dependent tasks
Parallel ≈ single latency Independent, merged Independent subtasks
MapReduce ≈ single latency Good for aggregation Large corpora
Section 4

Patterns: Debate and Consensus

Multi-agent debate: agents independently generate answers, then see each other's reasoning and update

Improves factual accuracy on questions where LLMs are overconfident

Adversarial: one agent argues for, one against — useful for due diligence, risk analysis

Pattern Agents Rounds Best for
Independent + vote N 1 Fast majority signal
Debate + update 2–4 2–3 Factual QA, reasoning
Adversarial 2 1–2 Risk analysis, contract review
Critic + revise 2 1 Writing quality, code review
Section 5

Communication and State

Message passing: agents communicate via structured messages (task, result, error, metadata)

Shared state: central state store (LangGraph checkpointer, Redis) that all agents read/write — enables handoffs

Blackboard pattern: shared memory space agents read from and write to; orchestrator polls for updates

Example: LangGraph multi-agent state with handoff

class MultiAgentState(TypedDict): messages: list current_agent: str research_output: str code_output: str def route_agent(state: MultiAgentState) -> str: if not state.get("research_output"): return "researcher" elif not state.get("code_output"): return "coder" return "reviewer"
Section 6

Trust and Verification

Agents can call untrusted tools, browse untrusted web pages, or receive attacker-controlled content → prompt injection risk

Cross-agent verification: second agent independently verifies first agent's output

Bounded permissions: code execution agent runs in sandbox, web agent can't access internal APIs

Human-in-the-loop checkpoints: pause before irreversible actions (send email, deploy code, make purchase)

Action type Risk Recommended control
Read-only (search, fetch) Low Log only
Write (create file, update DB) Medium Confirm schema + log
Irreversible (send, publish, delete) High Human approval required
Execute code High Sandboxed environment
Spend money Critical Hard limit + human approval
⚠
Never give a multi-agent system write access to production systems without human-in-the-loop checkpoints. The surface area for cascading errors is proportional to agent count squared.
Section 7

Evaluation and Observability

Multi-agent traces are hard to debug: which agent made the error? which communication hop corrupted the state?

Full trace logging: log every agent invocation with: agent ID, input state, output, latency, token usage

Eval approaches: end-to-end (final output quality), per-agent (each subagent evaluated independently), communication quality (are handoffs structured correctly?)
