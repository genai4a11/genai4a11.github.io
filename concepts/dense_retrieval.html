Dense Retrieval

ANN search over embeddings — DPR, bi-encoders, FAISS

📖 What It Is

Dense retrieval is a neural approach to finding relevant documents by encoding both queries and documents into dense vector representations (embeddings) and performing Approximate Nearest Neighbour (ANN) search in that vector space. Unlike sparse retrieval methods like BM25, which rely on exact term overlap, dense retrieval captures semantic similarity — "heart attack" matches "myocardial infarction" even though the words are completely different.

The technique was popularised by Facebook's Dense Passage Retrieval (DPR) paper (Karpukhin et al., 2020), which showed that a bi-encoder architecture — separate BERT encoders for query and passage — outperformed BM25 on open-domain QA tasks like Natural Questions and TriviaQA. The key insight: a shared embedding space lets you compare a short question against millions of long documents in milliseconds.

Modern dense retrievers use lightweight, efficient bi-encoder models such as BGE (BAAI General Embeddings), E5 (Microsoft), GTE (Alibaba), and commercial options like Cohere Embed and OpenAI text-embedding-3. These models are trained with contrastive learning (InfoNCE loss), pushing similar pairs together and dissimilar pairs apart in the embedding space.

At inference time, the corpus is embedded once and indexed — usually with FAISS (Facebook AI Similarity Search), HNSW, or a purpose-built vector database (Pinecone, Qdrant, Weaviate). Each query is encoded at runtime and an ANN lookup returns the top-k most similar documents in sub-millisecond to low-millisecond latency, even over billion-scale corpora.

🎯 When to Use It

Use Dense Retrieval when…Skip it (prefer BM25) when…
Queries use different vocabulary than the documents Users search for exact product codes, SKUs, or IDs
You need semantic / intent matching (Q&A, support) Your corpus has very rare technical terms or acronyms
Documents are in a domain with rich paraphrase variation You have no GPU budget for embedding your corpus
Multilingual retrieval (use multilingual models like mE5) Corpus changes every minute — re-indexing is too slow
💡 Production Advice

In practice, use Hybrid Search (dense + BM25 fused via Reciprocal Rank Fusion) by default — you get the best of both worlds. Pure dense retrieval can miss exact matches that BM25 would have caught.

The bi-encoder produces two independent embeddings — one for the query, one per document chunk. This is different from a cross-encoder (which concatenates query + document and is more accurate but cannot pre-compute document representations). The bi-encoder trade-off is speed vs. accuracy: fast ANN lookup, but slightly less precise ranking than a cross-encoder reranker.

💻 Code Example

End-to-end dense retrieval with sentence-transformers + FAISS:

# pip install sentence-transformers faiss-cpu numpy
from sentence_transformers import SentenceTransformer
import faiss, numpy as np

model = SentenceTransformer('BAAI/bge-small-en-v1.5')

# ── Offline: embed corpus once, save to disk ──────────────────
corpus = [
    'Dense retrieval uses bi-encoders for semantic search.',
    'FAISS enables billion-scale approximate nearest neighbour lookup.',
    'BM25 is sparse keyword retrieval — exact term matching only.',
    'Hybrid search fuses dense and sparse scores via RRF.',
    'Cross-encoders rerank top-k results with higher accuracy.',
]
# normalize_embeddings=True → L2-normalised, so IP == cosine sim
embs = model.encode(corpus, normalize_embeddings=True).astype('float32')
dim  = embs.shape[1]  # 384 for bge-small

index = faiss.IndexFlatIP(dim)   # exact search; use IndexIVFFlat at scale
index.add(embs)
# faiss.write_index(index, 'corpus.faiss')  # persist to disk

# ── Online: embed query, ANN lookup ──────────────────────────
query = 'How do vector databases find similar documents?'
q_emb = model.encode([query], normalize_embeddings=True).astype('float32')

scores, ids = index.search(q_emb, k=2)     # top-2 results
for score, idx in zip(scores[0], ids[0]):
    print(f'{score:.3f}  {corpus[idx]}')

# Expected output (approx):
# 0.823  FAISS enables billion-scale approximate nearest neighbour lookup.
# 0.761  Dense retrieval uses bi-encoders for semantic search.

Scaling to production

# Replace IndexFlatIP with an IVF index for billion-scale ANN:
nlist = 256  # number of Voronoi cells
quantizer = faiss.IndexFlatIP(dim)
index = faiss.IndexIVFFlat(quantizer, dim, nlist, faiss.METRIC_INNER_PRODUCT)
index.train(embs)          # must train on representative sample
index.nprobe = 32          # probe 32 cells at query time (speed/recall tradeoff)
index.add(embs)

🔀 Key Variants & Alternatives

  • Sparse retrieval (BM25) — Term-frequency keyword search. No embedding needed, lightning fast, great for exact matches. Use as baseline and combine via hybrid search.
  • Hybrid Search (Dense + BM25) — Fuse dense scores and BM25 scores with Reciprocal Rank Fusion (RRF). Best recall in production; should be your default.
  • Cross-encoder reranking — After dense retrieval returns top-50, run a cross-encoder on each (query, doc) pair for precise reranking. Adds ~100ms latency but significantly boosts nDCG.
  • HyDE (Hypothetical Document Embeddings) — Generate a hypothetical answer with an LLM, embed that, then search. Boosts recall for difficult queries.
  • ColBERT / Late Interaction — Retains token-level embeddings instead of a single CLS vector. Higher accuracy than bi-encoders, more storage cost.
  • SPLADE / Sparse-Dense hybrids — Learn sparse representations that can be indexed with inverted indices but retain semantic awareness.

⚠️ Common Gotchas

⚠️ Gotcha 1 — Forget to normalise

Using IndexFlatIP without normalising embeddings gives dot-product distance, not cosine similarity. Vectors with large norms dominate results regardless of direction. Always pass normalize_embeddings=True or call faiss.normalize_L2(embs) before indexing.

⚠️ Gotcha 2 — Re-embedding corpus at query time

Never embed the entire corpus on each request. Embed offline, persist the FAISS index to disk with faiss.write_index(), and load it once at startup. For dynamic corpora, use incremental indexing or a vector DB like Qdrant/Weaviate.

⚠️ Gotcha 3 — Wrong chunk size

Most bi-encoder models have a 512-token max context. Chunks longer than the context window are silently truncated — the tail of long documents is lost. Use 256-384 token chunks with 10-20% overlap as a starting point, then tune by measuring recall@k on your eval set.

⚠️ Gotcha 4 — Model mismatch at query vs. index time

If you re-embed queries with a different model than you used to build the index (e.g., after a model upgrade), all scores are meaningless — the embedding spaces are incompatible. Version your index alongside your model checkpoint.

⚠️ Gotcha 5 — Using a general model for a specialised domain

Off-the-shelf models (BGE, E5) are trained on general web data. For narrow domains (legal, medical, code), retrieval quality can be poor. Fine-tune on in-domain query-passage pairs with contrastive loss, or use domain-specific models.
