01 — Definition

What Is a Golden Dataset?

A golden dataset is a curated collection of question-and-answer pairs that reflects your application's use case — written by you, not by benchmark authors. Each example contains an input (a user question or prompt) and an expected correct answer defined by a human or domain expert.

Standardised BenchmarkGolden Dataset
Written byResearchersYou & your domain experts
Questions aboutGeneral knowledge / code / reasoningYour specific app and domain
Good forComparing models before you pick oneKnowing if your system works for your users
Run frequencyOnce — to pick a modelEvery model, prompt, or retriever change
Example question"What is the capital of France?""Can I return a digital download?"
💡 Key insight: A model can score 88% on MMLU and still fail to answer questions about your product's return policy. Only you know what "correct" looks like for your domain.
02 — Scoring

How Scoring Works: LLM-as-Judge

Because golden datasets can contain thousands of examples, human scoring at scale is impractical. The standard approach is LLM-as-Judge: a stronger or more trusted LLM (typically GPT-4o or Claude) evaluates the output of your application's LLM.

The judge reads three inputs — the original question, the expected answer, and the actual answer — then scores whether they match semantically, not word-for-word.

✓ Correct Expected: "30 days from purchase date" Actual: "You can return items within 30 days" → Same meaning, different words ✗ Wrong Expected: "No, digital downloads are non-refundable" Actual: "All purchases are eligible for return" → Contradicts the policy

For online evaluation (after deployment), where no expected answer exists, the judge evaluates faithfulness and relevance from the question, retrieved context, and response alone — no ground truth needed.

⚠️ Caveat: LLM-as-judge is reliable for format and consistency. For factual correctness in specialist domains (legal, medical, financial), human review on a sample remains necessary.
03 — Collection

How Teams Collect Golden Datasets

1

Real User Traffic — best source

Mining production logs is the highest-quality source because questions are real. Sample it, pick representative queries, and write correct answers manually.

  • Extract prompts from logs after privacy filtering
  • Sample across user segments, question types, and difficulty
  • Every production failure immediately becomes a test case
  • Refresh cadence: every 2 weeks to quarterly
Source: Getmaxim.ai; Statsig.com — Golden Datasets
2

Domain Expert Interviews

Sitting with subject matter experts — lawyers, support agents, doctors — produces the most nuanced and challenging test cases. Experts naturally surface edge cases you'd never invent.

  • Provide clear annotation guidelines with explicit rubrics
  • Include positive and negative examples — improves agreement by ~40%
  • Run calibration sessions before independent annotation
  • Assign critical samples to 3–5 annotators; use majority consensus
  • Target Cohen's kappa ≥ 0.7; below 0.4 means inadequate guidelines
Source: Booking.com Engineering; Arize Phoenix
3

Existing Documentation & FAQs

Convert knowledge base, policy documents, or FAQ pages directly into Q+A pairs. Fast to generate and gives good core coverage before real traffic is available.

  • E.g. "Q: What is the refund window? A: 30 days from purchase"
  • Good starting point to reach 20–50 pairs quickly
  • Ensures coverage reflects actual product usage patterns
4

Failure Analysis & Error Mining

When the system gives a wrong answer, capture it as a test case immediately. Over time this becomes the most targeted set because it's built from real failures.

  • Identify, categorise, and quantify failure modes systematically
  • Use active learning to target the most valuable cases
  • Generate root cause explanations for every error using an LLM
  • Never remove old failure cases — they form your regression suite
Source: Langfuse Blog — Error Analysis (2025)
5

Synthetic Generation

Use an LLM to generate Q+A pairs from your documents. Fast to scale but lower quality — models tend to generate easy questions and miss edge cases. Useful to bootstrap, not replace real queries.

  • RAGAS uses Evol-Instruct: simple, multi-context, and reasoning evolution
  • DeepEval provides synthetic data generation with diversity controls
  • Never use the same model for generation and validation
Source: Es et al. (2023) RAGAS; Lima et al. (2025) Know Your RAG
04 — Best Practices

Best Practices

📐 Dataset Size

  • Quality beats quantity — 500 good examples beat 10,000 noisy ones
  • 500–1,000 for judge optimisation (50/50 validation/test)
  • 100+ for development if questions cover full breadth
  • Include happy path, edge cases, and adversarial cases

🔄 Maintenance

  • Treat as a living document, not a one-time artefact
  • Favour small, frequent updates over rare large refreshes
  • Save foundational benchmarks immutably — create new versions
  • Keep a changelog for schemas and labelling guidelines

⚖️ Avoiding Bias

  • Assemble diverse annotation teams
  • Measure inter-annotator agreement (Cohen's kappa ≥ 0.7)
  • Run regular calibration sessions against gold-standard examples
  • Prevent data contamination — no overlap with model training data

🔁 Re-running

  • Run on every model, prompt, or retriever change
  • Run monthly to detect quality drift
  • Version prompts, datasets, and graders together
  • A score drop of > 5% warrants investigation before shipping

Recommended Starting Workflow

1Extract 100–200 diverse examples from production logs and known user failures
2Annotate with 3–5 domain experts using clear written guidelines and rubrics
3Measure inter-annotator agreement — target Cohen's kappa ≥ 0.7
4Build a lightweight annotation tool — teams with custom tools iterate ~10× faster (Husain, 2024)
5Establish an update cadence (every 2 weeks) with failure mining from production
6Supplement with RAGAS or DeepEval synthetic generation to fill edge-case gaps
7Run monthly to detect quality drift and catch regressions before users do
8Version all changes immutably for audit trail and reproducibility
