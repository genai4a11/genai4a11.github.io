Axolotl

finetuning ft_tools code

What It Is

Axolotl is an open-source Python library that wraps HuggingFace Transformers, PEFT, and TRL behind a single YAML configuration file. Instead of writing hundreds of lines of boilerplate training code, you describe your entire fine-tuning job — model, dataset, adapter settings, quantization, output format — in a declarative config and run one command. Axolotl handles the rest: dataset loading and formatting, tokenization, LoRA/QLoRA adapter injection, multi-GPU setup, and checkpointing.

It was created to lower the barrier for practitioners who want to fine-tune open-source LLMs (Llama, Mistral, Gemma, Phi, Qwen) without needing to re-implement the same training scaffolding every time. The project has become a community standard for reproducible fine-tuning experiments, partly because YAML configs are version-controllable and shareable — a config file is effectively a complete recipe for reproducing any training run.

Under the hood, Axolotl delegates to battle-tested libraries. Quantization is handled by bitsandbytes (4-bit NF4 for QLoRA). Adapter injection comes from PEFT. The actual training loop uses TRL's SFTTrainer or DPOTrainer depending on the training objective. Flash Attention 2 can be enabled with a single flag. Gradient checkpointing, DeepSpeed ZeRO, and FSDP are all supported through config fields, making it straightforward to scale from a single GPU to a multi-node cluster.

Axolotl supports multiple prompt formats out of the box — Alpaca, ShareGPT, ChatML, and raw completion — so you rarely need to write custom dataset preprocessing. For custom formats, you can provide a Python function. It also integrates with Weights & Biases for experiment tracking and supports pushing trained adapters directly to the HuggingFace Hub on completion.

The typical workflow is: pick a base model from HuggingFace Hub, prepare a dataset in JSONL format, write (or copy and edit) a YAML config, and run axolotl train config.yml. For most standard fine-tuning jobs on a single A100 or H100, this is genuinely the fastest path from dataset to trained adapter.

When to Use It

Use Axolotl when you want to fine-tune an open-source LLM for a specific task (instruction following, domain adaptation, chat style, function calling) and you want to move fast without reinventing training infrastructure. It is especially well-suited for:

  • LoRA and QLoRA experiments where you want to iterate quickly on rank, alpha, and target modules
  • Supervised fine-tuning (SFT) on instruction datasets in standard formats (Alpaca, ShareGPT, ChatML)
  • DPO and ORPO alignment training without writing custom reward pipelines
  • Teams that want reproducible, config-driven training pipelines checked into version control
  • Running on cloud spot instances (Modal, RunPod, Lambda Labs) where you need a reliable, restartable training job

Axolotl is less appropriate when you need highly custom training loops, non-standard model architectures, or when you're doing pre-training from scratch at scale (use Megatron-LM or NeMo for that).

Full Code Example

A minimal QLoRA fine-tuning setup with Axolotl. Save as config.yml then run axolotl train config.yml:

# config.yml — Axolotl QLoRA fine-tuning on Llama-3.1-8B
# pip install axolotl[flash-attn,deepspeed]

base_model: meta-llama/Meta-Llama-3.1-8B
model_type: LlamaForCausalLM
tokenizer_type: AutoTokenizer

# 4-bit QLoRA quantization
load_in_4bit: true
adapter: lora

lora_r: 32
lora_alpha: 64
lora_dropout: 0.05
lora_target_modules:
  - q_proj
  - k_proj
  - v_proj
  - o_proj
  - gate_proj
  - up_proj
  - down_proj

# Dataset — ShareGPT format JSONL
datasets:
  - path: ./data/train.jsonl
    type: sharegpt
    conversation: chatml

dataset_prepared_path: ./prepared_data
val_set_size: 0.02
sequence_len: 4096
sample_packing: true       # Pack short examples to fill context — improves GPU util

# Training
num_epochs: 3
micro_batch_size: 2
gradient_accumulation_steps: 4
learning_rate: 2e-4
lr_scheduler: cosine
warmup_steps: 50
optimizer: adamw_bnb_8bit  # 8-bit Adam saves memory

# Efficiency
flash_attention: true
gradient_checkpointing: true
bf16: true
tf32: true

# Output
output_dir: ./axolotl-output
save_steps: 100
eval_steps: 100
logging_steps: 10

# Optional: push adapter to HF Hub on completion
# hub_model_id: your-username/my-fine-tuned-model
# hub_strategy: end

# Experiment tracking
wandb_project: axolotl-runs
wandb_name: llama3.1-8b-qlora-run1

To run training (single GPU):

# Install
pip install axolotl[flash-attn]

# Train
axolotl train config.yml

# Resume from checkpoint if interrupted
axolotl train config.yml --resume-from-checkpoint ./axolotl-output/checkpoint-200

# Merge LoRA adapter back into base model weights
axolotl merge-lora config.yml --lora-model-dir ./axolotl-output

# Inference test after training
axolotl inference config.yml --lora-model-dir ./axolotl-output \
  --prompter ShareGPT --message "Explain gradient checkpointing"

Python API for programmatic use:

# You can also drive Axolotl from Python (useful in notebooks / CI)
from axolotl.cli import do_train
from axolotl.utils.config import normalize_config
from omegaconf import OmegaConf

cfg = OmegaConf.load("config.yml")
cfg = normalize_config(cfg)
do_train(cfg)

# Or use the lower-level HF objects Axolotl builds for you:
from axolotl.utils.models import load_model, load_tokenizer
from axolotl.utils.data import prepare_dataset

tokenizer = load_tokenizer(cfg)
model, _ = load_model(cfg, tokenizer)
train_dataset, eval_dataset = prepare_dataset(cfg, tokenizer)
# ... hand off to your own Trainer if needed

Key Variants & Alternatives

  • Unsloth — Faster training (2–5×) via hand-written CUDA kernels. Great for speed; less config flexibility than Axolotl. Can be used as the backend inside Axolotl.
  • LLaMA-Factory — Similar YAML-driven approach with a web UI. Broader model coverage; slightly less community-tested than Axolotl.
  • TRL (raw) — More control, more boilerplate. Use when Axolotl's abstractions get in the way of custom training objectives.
  • torchtune — PyTorch-native, from Meta. More explicit and transparent; better for research; less plug-and-play than Axolotl.
  • Modal / RunPod + Axolotl — Common production pattern: run Axolotl inside a containerised cloud GPU job for cost-effective spot-instance training.

Common Gotchas

  • sample_packing + eval hang — Set eval_sample_packing: false in your config. Evaluation with packing enabled can deadlock or produce incorrect metrics.
  • Sequence length vs GPU memory — sequence_len: 4096 with a 7B model in 4-bit needs ~18–20 GB VRAM with packing + gradient checkpointing. Reduce sequence_len before reducing batch size if you OOM.
  • Chat template mismatch — Using type: sharegpt with a model that expects Llama-3 instruct format will produce garbled outputs. Always check tokenizer.chat_template matches your dataset type.
  • Missing EOS token loss — Axolotl trains on loss over the full sequence by default. Set train_on_inputs: false to mask the prompt tokens and only compute loss on completions — this almost always gives better results for instruction tuning.
  • LoRA rank too low for complex tasks — r=8 or r=16 works for style and format; for domain-specific knowledge (medical, legal, code), use r=64 or r=128 with correspondingly higher alpha.
