Section 1

What is Function Calling?

Function calling (tool use): LLM generates a structured call to an external function instead of a text response. The system executes the function and feeds the result back into context.

The model does not execute code — it generates JSON describing which function to call and with what arguments. Your code does the execution.

Three formats: OpenAI tools API, Anthropic tool_use blocks, and open-source models via system prompt engineering

Example: define a tool and handle its call (OpenAI)

from openai import OpenAI import json client = OpenAI() tools = [{ "type": "function", "function": { "name": "get_weather", "description": "Get the current weather for a city", "parameters": { "type": "object", "properties": { "city": {"type": "string", "description": "City name"}, "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]} }, "required": ["city"] } } }] response = client.chat.completions.create( model="gpt-4o", messages=[{"role":"user","content":"What's the weather in Paris?"}], tools=tools, tool_choice="auto" ) if response.choices[0].message.tool_calls: call = response.choices[0].message.tool_calls[0] args = json.loads(call.function.arguments) result = get_weather(args["city"], args.get("unit", "celsius"))
Section 2

The Tool Loop

Single-turn tool call: user message → model generates tool call → your code executes → result fed back → model generates final answer

Multi-turn: model may chain multiple tool calls before generating final answer

Example: full tool loop implementation

def run_tool_loop(messages, tools, max_iterations=10): for _ in range(max_iterations): response = client.chat.completions.create( model="gpt-4o", messages=messages, tools=tools) msg = response.choices[0].message messages.append(msg) if not msg.tool_calls: # model is done return msg.content for tool_call in msg.tool_calls: result = dispatch_tool(tool_call.function.name, json.loads(tool_call.function.arguments)) messages.append({ "role": "tool", "tool_call_id": tool_call.id, "content": json.dumps(result) }) return "Max iterations reached"
✓
Always wrap tool execution in try/except. Feed the error message back to the model in the tool result — models can recover from errors and try a different approach.
Section 3

Tool Schema Design

Tool description quality directly determines call accuracy. Vague descriptions → wrong tool selection.

Principles:

  • Name is a verb phrase ("search_web", not "web")
  • Description explains WHEN to use it, not just what it does
  • Parameters have description + examples for non-obvious args
  • Use enum for categorical values

Example: good vs bad tool descriptions

# BAD: vague, no guidance on when to use {"name": "search", "description": "Search for things"} # GOOD: specific, with when-to-use context {"name": "web_search", "description": "Search the internet for current information, news, or facts that may have changed since training. Use when the user asks about recent events, current prices, or anything time-sensitive.", "parameters": { "query": {"type": "string", "description": "Specific search query. Be specific — 'Tesla stock price today' not just 'Tesla'"}, "num_results": {"type": "integer", "default": 5, "description": "Number of results to return (1-10)"} }}
Aspect Bad Good
Name "data" "fetch_user_profile"
Description "Gets data" "Retrieve user profile by ID. Use when you need name, email, or account status."
Parameter desc "id" "user_id: UUID string from the users table, e.g. '550e8400-e29b-41d4-a716'"
When to use Not stated Explicitly stated
Section 4

Parallel Tool Calls

GPT-4o and Claude 3+ support parallel tool calls: model generates multiple tool calls in one response

Use case: independent queries that can be executed simultaneously

Example: parallel tool call handling

# Model may return multiple tool calls at once tool_calls = response.choices[0].message.tool_calls # e.g. [get_weather("Paris"), get_weather("London"), get_time("Paris")] import asyncio async def execute_all(tool_calls): tasks = [dispatch_tool_async(tc.function.name, json.loads(tc.function.arguments)) for tc in tool_calls] return await asyncio.gather(*tasks) results = asyncio.run(execute_all(tool_calls))
⚠
Parallel tool calls require your executor to handle concurrent requests correctly. If tools touch shared state (e.g., database writes), handle conflicts explicitly.
Section 5

Structured Outputs and Strict Mode

Strict mode (OpenAI): guarantees model output exactly matches your JSON schema. No extra fields, no missing required fields.

Anthropic tool_use: similar guarantee — model always returns valid tool_use blocks matching the schema

When to use strict: any time you need to parse the output programmatically (>95% of production use cases)

Example: OpenAI strict structured output

from openai import OpenAI from pydantic import BaseModel client = OpenAI() class ResearchResult(BaseModel): title: str summary: str confidence: float sources: list[str] response = client.beta.chat.completions.parse( model="gpt-4o", messages=[{"role":"user","content":"Research quantum computing"}], response_format=ResearchResult ) result = response.choices[0].message.parsed # typed ResearchResult object
Section 6

Tool Selection Failure Modes

Wrong tool selected

Model calls "search" when it should call "database_lookup". Fix: improve tool descriptions, add "do NOT use for X" guidance, reduce total tool count.

Hallucinated arguments

Model generates a plausible-looking but invalid argument (non-existent ID, wrong enum value). Fix: strict schema mode + validate before execution.

Infinite tool loop

Model keeps calling tools without reaching a final answer. Fix: max_iterations guard, explicit "finish" tool, or detect repeated identical calls.

Tool result ignored

Model generates final answer before incorporating tool result. Fix: use tool_choice="required" when tools are mandatory, or structure the prompt to force tool use.

Best practices for production:

  • Rate limiting: cache frequent identical tool calls (same weather query per city per hour)
  • Tool versioning: tools are part of your API contract with the model. Schema changes can break existing deployments.
  • Observability: log every tool call (name, args, result, latency) to your trace store
