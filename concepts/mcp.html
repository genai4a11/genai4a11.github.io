SECTION 01

What is MCP

The Model Context Protocol (MCP) is an open-source standard developed by Anthropic that enables LLM applications (called "hosts") to securely connect with and invoke capabilities from external servers. Before MCP, each AI application had to implement custom integrations for every tool or data source—a fragmented, difficult-to-scale approach. MCP standardizes this connection layer via JSON-RPC 2.0 over stdio (local) or Server-Sent Events (SSE) over HTTP.

At its core, MCP solves two problems: (1) capability discovery—how does an LLM learn what a server can do?—and (2) secure invocation—how does the host safely execute server capabilities on behalf of the user? The protocol is transport-agnostic, language-agnostic, and designed for both local and remote scenarios.

MCP is already integrated into Claude Desktop, Cursor, VS Code, and third-party agents. It represents a shift toward a standardized, composable agent ecosystem where tools and data sources are first-class citizens that LLMs can dynamically invoke without hard-coded integrations.

Why This Matters MCP eliminates the need to rebuild integrations for every AI framework. A single MCP server for "read GitHub issues" works with Claude, Cursor, custom agents, and future tools. This dramatically reduces development friction and enables rapid prototyping of AI workflows.
SECTION 02

Core Primitives: Resources, Tools & Prompts

MCP defines three fundamental primitives that servers expose to hosts:

1. Resources are read-only or read-write data that servers manage. Examples: file contents, database records, API responses, or knowledge bases. Resources are named with URIs (e.g., `file://path/to/document.txt`) and can be hierarchically listed or directly accessed. A resource's text representation is sent to the LLM as context, enabling the model to reason over data without the server executing complex logic.

2. Tools are callable functions that perform side effects: creating files, sending emails, querying APIs, or executing commands. Tools have schemas (JSON Schema) that describe inputs, and hosts use these schemas to construct valid invocations. When the LLM decides a tool is relevant, the host calls it and returns the result back to the model.

3. Prompts are templates that the host can request from the server. A prompt is a reusable instruction or example set that contextualizes the LLM's behavior. For example, a "write-sql-query" prompt might include a schema and example queries, priming the model to generate accurate SQL.

Beyond these primitives, MCP defines two key roles: the server (exposes resources, tools, prompts) and the host (client that connects, discovers capabilities, and invokes them on behalf of users). Some implementations also define a transport layer (stdio, SSE, or WebSocket) that carries JSON-RPC messages between server and host.

Composition Pattern A single host (like Claude Desktop) can connect to multiple MCP servers simultaneously. For example: one server provides file system access, another handles GitHub integration, and a third exposes a Postgres database. The LLM sees all three servers' capabilities as a unified toolkit.
SECTION 03

Architecture Deep Dive

MCP uses JSON-RPC 2.0, a lightweight protocol that sends method calls and responses as JSON objects. Over stdio (for local servers), the host spawns a server process and communicates via stdin/stdout. Each line of output is a complete JSON-RPC message. For remote servers, communication happens over HTTP Server-Sent Events (SSE), where the server streams updates back to the host.

The protocol flow begins with initialization: the host sends an `initialize` request, and the server responds with its capabilities (which resources, tools, and prompts it offers, plus protocol version and metadata). This enables capability negotiation—the host can decide whether the server is useful for the current context.

Once initialized, the host can discover and list resources and tools (using `resources/list`, `tools/list`, `prompts/list`), read resources (using `resources/read`), call tools (using `tools/call`), or request prompts (using `prompts/get`). All calls are JSON-RPC method invocations, and responses include either a result or an error. The server may also send unsolicited notifications (e.g., "resource was updated") to keep the host informed.

JSON-RPC Request/Response Example: Host → Server (initialize): { "jsonrpc": "2.0", "id": 1, "method": "initialize", "params": { "protocolVersion": "2024-11-05", "capabilities": {}, "clientInfo": { "name": "Claude Desktop", "version": "0.7.0" } } } Server → Host (response): { "jsonrpc": "2.0", "id": 1, "result": { "protocolVersion": "2024-11-05", "capabilities": { "tools": {}, "resources": {}, "prompts": {} }, "serverInfo": { "name": "my-server", "version": "1.0.0" } } }

MCP also supports incremental reading of large resources (via byte ranges) and sampling (where the LLM can ask the server to execute a model call, useful for complex reasoning tasks). The protocol is designed to be minimal yet extensible, allowing future versions to add new primitives without breaking existing clients.

Transport Matters Stdio is fast (no network latency) and ideal for local tools. SSE and WebSocket are suitable for remote or browser-based hosts. Choose based on your deployment model: embedded tools use stdio; cloud services use HTTP transports.
SECTION 04

Building an MCP Server in Python

The Anthropic MCP Python SDK makes building servers straightforward. You define resources and tools as decorated functions, and the SDK handles JSON-RPC serialization and transport. Here's a complete working example that exposes a tool and a resource:

from mcp.server import Server from mcp.types import ( Tool, TextContent, ToolResult, Resource ) import json # Create a server instance server = Server("my-server") # Define a tool @server.call_tool() def calculate_factorial(n: int) -> int: """Calculate n!""" if n < 0: raise ValueError("n must be >= 0") result = 1 for i in range(1, n + 1): result *= i return result # Alternatively, use explicit tool definition factorial_tool = Tool( name="factorial", description="Compute n!", inputSchema={ "type": "object", "properties": { "n": {"type": "integer", "description": "Input number"} }, "required": ["n"] } ) @server.register_tool(factorial_tool) def handle_factorial(n: int) -> ToolResult: try: result = 1 for i in range(1, n + 1): result *= i return ToolResult( content=[TextContent(type="text", text=str(result))], isError=False ) except Exception as e: return ToolResult( content=[TextContent(type="text", text=str(e))], isError=True ) # Define a resource knowledge_base = Resource( uri="resource://knowledge/faq", name="FAQ", description="Frequently asked questions", mimeType="text/plain" ) @server.register_resource(knowledge_base) def get_faq() -> str: return """Q: What is MCP? A: Model Context Protocol is an open standard... Q: How do I build a server? A: Use the Python SDK and define tools/resources...""" # Run the server over stdio server.run_stdio()

When the host connects, it discovers your tools and resources via the initialize handshake. The LLM can then invoke `calculate_factorial` or read the FAQ resource. The SDK handles all JSON-RPC serialization, error handling, and capability negotiation automatically.

For more complex scenarios, you can: (1) stream large resources incrementally, (2) implement resource change notifications to push updates to the host, (3) add authentication/authorization checks in tool handlers, and (4) use the `prompt` registry to define LLM instruction templates. The SDK also supports async functions, making it easy to integrate with external APIs (e.g., calling `asyncio` to fetch from databases).

Deployment Tips Run your MCP server as a subprocess from the host (e.g., `subprocess.Popen(["python", "server.py"])`). For remote servers, wrap it in an HTTP server using frameworks like FastAPI and configure the host to connect over SSE. Always version your server API and include clear error messages.
SECTION 05

MCP vs Custom APIs

Before MCP, every LLM integration required hand-rolled API clients. Comparing MCP to custom point-to-point integrations reveals why standardization matters:

Aspect MCP Custom API
Standardization Open protocol; works with any compatible host Bespoke per integration; no reusability
Discoverability Host learns capabilities via introspection Hard-coded or documented offline
Multi-Client Reuse One server supports Claude, Cursor, agents, etc. Must reimplement for each client
Transport Stdio (local) or SSE/WebSocket (remote) REST, gRPC, or other—varies per integration
Auth/Rate Limiting Standardized patterns; easier to implement Custom per service; complex at scale
Evolution Graceful versioning; backward-compatible updates Breaking changes require client updates

In practice, MCP shines for tool and data source integrations where you want an LLM to have optional, composable access. Custom APIs remain necessary for stateful protocols (e.g., real-time bidirectional communication) or when performance optimization (e.g., binary protocols) outweighs standardization benefits.

When to Use MCP Use MCP for read/write access to databases, file systems, APIs, or knowledge bases. It's ideal for tools that are invoked occasionally and where the LLM drives the interaction. Custom APIs are better for streaming, WebSocket, or low-latency scenarios.
SECTION 06

Ecosystem & Existing Clients

Claude Desktop is the flagship MCP host, released in early 2024. Users configure MCP servers in a JSON file (`claude_desktop_config.json`) and Claude automatically discovers and uses them. This enabled integrations with filesystem access, web search, code repositories, and more without requiring code changes.

Cursor, an AI-powered code editor, integrated MCP support to let developers add custom tools for code generation, testing, and deployment. VS Code and community-built agents also support MCP, expanding the ecosystem. The MCP Registry (at modelcontextprotocol.io) lists public servers: filesystem access, GitHub API wrapper, PostgreSQL interface, Brave Search, DuckDuckGo, Puppeteer (web scraping), Stripe API, and many more contributed by the community.

This ecosystem growth demonstrates MCP's value: a single "read GitHub issues" server built once can be reused across all MCP-compatible applications, eliminating integration duplication.

Claude Desktop Config Example (claude_desktop_config.json): { "mcpServers": { "filesystem": { "command": "python", "args": ["-m", "mcp_server_filesystem"] }, "postgres": { "command": "python", "args": ["-m", "mcp_server_postgres"], "env": { "DATABASE_URL": "postgresql://user:pass@localhost/mydb" } }, "github": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"], "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" } } } } After updating this config, Claude Desktop auto-loads all three servers and the LLM can read files, query the database, and fetch GitHub data.
Community Growth The MCP community is rapidly building integrations for popular services. Before writing a custom server, check the MCP Registry to see if someone has already solved your use case. Contributing back to the community strengthens the ecosystem.
SECTION 07

Production Patterns & Security

Deploying MCP servers in production requires careful consideration of security, reliability, and observability. Here are key patterns:

Authentication & Authorization: MCP servers should validate that the connecting host is authorized. For local stdio connections, OS-level process permissions provide baseline isolation. For remote (HTTP) servers, use OAuth 2.0 or API keys. Within tool handlers, implement fine-grained authorization: does the user have permission to execute this tool or read this resource?

Auth Example in Tool Handler: def handle_tool_call(tool_name: str, params: dict) -> ToolResult: # Extract user context from request user_id = get_request_context().user_id # Check authorization if tool_name == "delete_file" and not has_permission(user_id, "admin"): return ToolResult( content=[TextContent(type="text", text="Unauthorized")], isError=True ) # Proceed with tool execution path = params.get("path") os.remove(path) return ToolResult( content=[TextContent(type="text", text=f"Deleted {path}")], isError=False )

Rate Limiting: Prevent abuse by limiting tool invocations per user/time window. Implement token-bucket or sliding-window algorithms. If a tool integrates with a third-party API (e.g., OpenAI, GitHub), respect that service's rate limits and implement exponential backoff.

Server Versioning: Include a `protocolVersion` in your server's initialization response. When you change tool signatures or resource schemas, increment the version. Hosts can use this to decide whether to continue or upgrade.

Observability: Log all tool invocations (inputs, outputs, errors) for auditing and debugging. Use structured logging (JSON) and ship logs to a centralized service. Monitor resource usage (CPU, memory, file handles) to detect resource leaks or misbehaving clients.

Error Handling: Return meaningful error messages in tool results. If a database query fails, include the error reason (not the full stack trace, which leaks information). Use consistent error schemas so hosts can programmatically handle failures.

Resource Isolation Be cautious with tools that grant broad access (e.g., "execute arbitrary command" or "read any file"). Scope permissions tightly: if a tool is "read customer support tickets," don't let it read HR files. Use sandboxing (containers, chroots) if running untrusted code.

Testing & Deployment: Unit-test tool handlers independently. Integration-test the full server with mock hosts. Deploy to staging first and verify with a small group of hosts before rolling out to production. Use canary deployments to roll out server updates gradually.

Best Practice Summary Treat MCP servers as microservices: version them, monitor them, log them, and secure them. Use automation (CI/CD) to test before deployment. Document all tools and resources clearly so hosts can reason about side effects. When in doubt, ask for explicit user confirmation before executing dangerous operations.
